# ADR-034: The pictures and models reach the live site from Vercel Blob behind the CDN

- Status: accepted (owner decisions 2026-11-10: "Yes, publish them"; "In uploading all images to the site, use the Vercel Blob store instead, as agreed")
- Date: 2026-11-10
- Deciders: owner, Claude Code session 2026-11-10

## Context

The site went live at coppercork.com on 2026-11-10 with words and data only (ADR-033). Every CIG picture and model the site can show is local by design: `scripts/media/fetch-*.ts` copy RSI's ship-matrix images and Comm-Link covers, the wiki's gallery pictures, RSI's holoviewer models and the wiki's title icons into git-ignored `fixtures/` folders (ADR-009, ADR-017, ADR-024, ADR-025, ADR-029), and `scripts/media/prepare.ts` builds them into git-ignored `apps/web/public/media/`: WebP renditions at several widths, meshopt glTF models, five render loops, and a `manifest.json` the site reads at build through `apps/web/lib/media.ts`. On the owner's machine that is about 12,000 files and 1.7 GB. A deploy has none of it, so the live site rendered bare, and the owner, having seen it bare, wants the pictures.

The constraints:

- CLAUDE.md section 2: "Never route models, textures, thumbnails, or other large assets through the app server. They are served from object storage behind the CDN." Vercel's static file serving is the app server; 1.7 GB is also far past what a deployment should carry, and the media must never enter git.
- CLAUDE.md section 9 named Cloudflare R2 (`R2_*`, `CDN_BASE_URL`), validated in `packages/schema/env.ts`; spec 01's publish step and ADR-001 meant R2 for the data pack. None of it was provisioned. The owner has no Cloudflare account (the earlier Coppercork site ran on Vercel and Neon alone); the site's Vercel project exists and the owner's Vercel team is on Pro (ADR-033).
- The media are CIG's. `docs/legal/cig-approval.md` had the "RSI website images", "Wiki gallery pictures", "RSI holoviewer models" and "Title icons" boxes unticked, with no CIG writing on file; each said "local development only until ticked". The owner's standing direction is to build as if approved (ADR-019), and he ticked the Spectrum republication box on his own word on 2026-11-10. Publishing CIG's pictures to a public address is his explicit call, not a consequence of ADR-019.
- The renditions are not content-addressed. `prepare.ts` names them by entity and width (`/media/ships/aegs_gladius-1280.webp`), and rebuilds the same name with new bytes when RSI changes a picture. A long cache lifetime on those names would show stale pictures for as long as the lifetime.
- The holoviewer loads its models with `fetch` (three.js `GLTFLoader`), which is a cross-origin request once the models live on another host; `<img>` and `<video>` are not.

## Decision

The built media are published to the Vercel Blob store `sc-hub-media`, connected to the `sc-hub` project, and served to browsers from the store's public address (`CDN_BASE_URL`, `https://<store>.public.blob.vercel-storage.com`), which Vercel's edge network caches; the site never serves a picture or a model itself.

**Publishing** is `scripts/media/publish.ts`, run by hand on the owner's machine after `prepare.ts`, never from CI: CI has neither the media nor credentials. It reads its credentials from `.env.local` at the repository root: either `BLOB_READ_WRITE_TOKEN`, or the pair `vercel env pull` writes, `BLOB_STORE_ID` with a short-lived `VERCEL_OIDC_TOKEN` (the store's token is marked sensitive on the project, so the pull writes `[SENSITIVE]` in its place and the OIDC pair is the way in; the connection has to include the Development environment for that). It prints no credential; the summary line names the store's public address, which is not a secret. Every file is **content-addressed**: `/media/ships/aegs_gladius-1280.webp` is uploaded as `media/ships/aegs_gladius-1280-<first twelve hex of its SHA-256>.webp`, with its content type and a one-year cache lifetime, and the manifest is rewritten to those keys (`scripts/media/publish-plan.ts`) and validated against `MediaManifest` before it goes up last, as `media/manifest.json` with a five-minute lifetime (`scripts/media/publish-sync.ts`). A key's bytes therefore never change: the edge and browsers may hold them for a year, a changed picture gets a new key instead of a stale copy, and a run uploads only the keys the store lacks, so it is idempotent and an interrupted run resumes. The upload hashes the bytes it reads and refuses when they differ from the planned key, so a `prepare.ts` running in the same folder cannot fill an immutable key with other bytes. Objects the new manifest no longer names are counted, and deleted only with `--prune` on a run whose manifest did not change: the live site names the old keys until its next build fetches the new manifest. The run ends by reading the manifest back through the CDN and asking for one object with an `Origin`, as a browser would, and reports what it saw. The store is reached through the `@vercel/blob` SDK behind a four-method interface (`scripts/media/blob.ts`), so the sync is unit-tested against an in-memory store with no network.

**The site** reads `CDN_BASE_URL` (validated as an http(s) URL) in `apps/web/lib/media.ts`. A local build, `public/media/manifest.json`, wins and names local files, as before. Without one, `apps/web/scripts/media-manifest.ts` fetches `${CDN_BASE_URL}/media/manifest.json` before `next build` and `next dev`, validates it against the schema, and writes it to git-ignored `apps/web/generated/media-manifest.json`; `loadMediaManifest` reads that copy and prefixes every `/media/` path in it with `CDN_BASE_URL`, so every `src`, `srcset`, `<video src>` and model URL on every page points at the CDN. A fetch that fails, or a manifest that does not validate, fails the build: a deploy configured for pictures and silently published without them is a broken deploy, and Vercel keeps the previous one live. Without `CDN_BASE_URL` nothing changes from ADR-009: no pictures. There are no rewrites, no proxy routes and no image optimizer in front of the CDN (`images.unoptimized` stays).

**On Vercel**, `CDN_BASE_URL` is the one media variable the site reads, set for production and preview. The store's own variables (`BLOB_READ_WRITE_TOKEN`, `BLOB_STORE_ID`, `BLOB_WEBHOOK_PUBLIC_KEY`) are on the project because the store is connected; nothing in `apps/web` reads them.

### The owner's decision

Publishing CIG's pictures and models to a public address is the owner's explicit decision, recorded here and in `docs/legal/cig-approval.md` before anything was uploaded. Asked on 2026-11-10 "Publish CIG's pictures and models on the live site, ticking the four imagery boxes on your word?", the owner answered "Yes, publish them"; in the session doing the work he directed, the same day, "In uploading all images to the site, use the Vercel Blob store instead, as agreed." The four boxes (RSI website images, RSI holoviewer models, wiki gallery pictures, title icons) are ticked on those words with that date; no written confirmation from CIG is on file, and ADR-019 is the standing direction. The "Game-extracted 3D models and textures" box is untouched: nothing from `Data.p4k` is published.

## Alternatives considered

| Option | Why not |
| --- | --- |
| Cloudflare R2 behind a custom domain, as CLAUDE.md section 9 and spec 00 assumed | The owner chose Vercel Blob ("great let's go with vercel blob then", 2026-11-10): he has no Cloudflare account, R2 wants a payment method on file even at no charge, Vercel is the one account he pays for, the store connects to the project he already runs, and a custom domain would have meant moving coppercork.com's DNS to Cloudflare. The trade: Blob bills bandwidth past the plan's allowance, R2 would not; moving later is a re-upload and one variable, since the manifest keeps relative paths. The first version of this work was written for R2 (a hand-rolled SigV4 client) and replaced the same day. `R2_*` stays in CLAUDE.md for the data pack, which spec 01 still aims at R2 and which no ADR has decided |
| Commit the media, or copy them into the deploy | 1.7 GB in git or in every Vercel build; CLAUDE.md section 2 forbids serving them from the app server; every media folder is git-ignored by earlier ADRs for reasons that stand |
| Mirror the local paths as store keys with a year's cache | The names are not content-addressed; a changed picture at the same name would be stale at the edge and in browsers for a year. With a short lifetime instead, the CDN would help little. Content addressing at publish costs forty lines and makes idempotence a key lookup |
| Content-address in `prepare.ts` so local paths are hashed too | Touches every rendition path function, the schema's path comments and the e2e records for no local gain: local files are served by `next dev` from disk and need no cache busting. Hashing where the lifetime matters, at publish, leaves the local build as it was |
| Resolve a local manifest against `CDN_BASE_URL` as well | Its paths name local, unhashed files that are not in the store; resolving them would 404. The manifest and the files it names travel together, so the fetched manifest is resolved and a local one is not |
| Fetch the manifest at request time, or `fetch` in `loadMediaManifest` | `loadMediaManifest` is synchronous and called from many server components during static generation; the build step keeps it so, and keeps a flaky CDN from making pages differ |
| Proxy `/media/*` through a Next rewrite to the store | Routes every byte through the app server; CLAUDE.md section 2 names exactly this |
| Random suffixes on blob names (the SDK's default) | The key must be derived from the content so a repeat run can tell what is already there; the suffix is off and the hash does that job |
| Wait for CIG's written approval before publishing | The owner's call; the boxes record what he decided |

## Consequences

- The live site shows every picture and model the owner's machine has built, from the CDN. Pages that had no picture before (concepts without a matrix image, ships without a gallery) still have none; nothing here changes what the manifest lists.
- Publishing is a two-step owner routine after a media refresh: `pnpm exec tsx scripts/media/prepare.ts` then `pnpm exec tsx scripts/media/publish.ts`, from the checkout that holds the complete `fixtures/` copies, then a Vercel deploy (any push to `main`, or a redeploy) picks the new manifest up at build. `docs/runbooks/media.md` has the steps. Until that redeploy, the live site keeps the manifest its build fetched; a publish alone changes nothing on the site, by design.
- A Vercel build now makes one request to the store and fails if it cannot. Vercel keeps the previous deployment live on a failed build.
- Old keys accumulate in the store until a `--prune` run; at Blob's storage price that is cents a month, and keeping them means a rolled-back deployment's manifest still resolves. `--prune` therefore runs only on a later run, after the site has redeployed on the new manifest, never in the run that changed it; the script refuses otherwise.
- Bandwidth past the Vercel plan's allowance is billed; the content-addressed keys let browsers and the edge hold every picture for a year, which is the main lever on it. R2 would not have billed bandwidth; the move, if it ever pays, is a re-upload and a change of `CDN_BASE_URL`.
- The store is public: anyone may hotlink the files. They are CIG's public pictures, credited on the site; the exposure is the same as RSI's own media host.
- Spec 00's "Infrastructure provisioned" criterion is enabled, not met: its object-store part is met by the Blob store the owner created (the criterion says "R2 bucket with CDN domain", which this supersedes for the media), and Neon and Fly remain; it stays unticked. Spec 02's "Performance" criterion, "images served from R2 with width-appropriate variants", is now true in substance with Blob in R2's place and stays unticked until its Lighthouse half is measured. Spec 05's "Caching" criterion, "models and images immutable with versioned paths", is met for the media by the content-addressed keys.
- CLAUDE.md section 9: the Vercel row gains `CDN_BASE_URL`; the variable list gains `BLOB_READ_WRITE_TOKEN` and `BLOB_STORE_ID` and says what each store is for. `.env.example` says the same. ADR-033's media note and `docs/runbooks/launch.md`'s media row point here. `@vercel/blob` joins the root dev dependencies for the publish script alone.
- The e2e records and CI are unchanged: CI has no `CDN_BASE_URL`, so its builds behave as before, and `media.spec.ts` still holds either way.
- Implemented by PR 45 (https://github.com/ember-arch/sc-hub/pull/45).
