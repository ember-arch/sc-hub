# ADR-051: New Comm-Links get their cover from the News workflow, merged into the live manifest

- Status: accepted; the secret `BLOB_READ_WRITE_TOKEN` was added by the owner on 2026-11-11
- Number: merged as ADR-048 (PR 65), the same number the lowercase c had taken an hour earlier (PR 64); renumbered ADR-051 the same day, with every reference to it
- Date: 2026-11-11
- Deciders: owner (reported on 2026-11-11 that the dispatch "Monthly Store Bundle 2026", Comm-Link 20943, had no picture; a session of the same day asked that new Comm-Links get their cover without a hand publish), Claude Code session 2026-11-11
- Amends: ADR-029 ("a cover appears after a local run of the fetch"), ADR-034 ("publishing is run by hand ... never from CI"; the manifest's last writer wins), CLAUDE.md sections 4 and 9

## Context

The News workflow collects a new Comm-Link within two hours of RSI publishing it (ADR-027), but its cover reached the site only when the owner's machine ran `fetch-covers.ts`, `prepare.ts` and `publish.ts` (ADR-029, ADR-034). On 2026-11-11 the dispatch 20943 sat on the front page with no picture until a session did that by hand (manifest 2026-11-11T15:23:27Z, 110 covers).

CI cannot run the hand routine. `prepare.ts` rebuilds the whole manifest from the complete, git-ignored `fixtures/` (about 12,000 files): in CI it would build a manifest of nothing, and publishing that would take every picture off the site. The manifest, `media/manifest.json`, is the store's one mutable object, and until now its last writer won.

What the store offers: `@vercel/blob` 2.9 returns the store's own, strong ETag from its API (`head`) and writes conditionally (`put` with `ifMatch`, refused with a 412 when the object has changed). Checked against the real store on 2026-11-11 with a throwaway key outside `media/` (deleted afterwards): the right ETag wrote, a stale one was refused with 412. The bytes come only through the public URL, which is the edge: `get`'s `useCache: false` works for private stores only (the store answers 400 to `cache=0` on a public one), and the edge ignores query strings (the live manifest answered `HIT` with an `Age` of about 7,000 s to random ones). The edge keeps the manifest well past its 300 s `max-age` and drops it when an overwrite purges it; on the throwaway key the new bytes were served at once. `get`'s ETag is the edge's, weakened (`W/"..."`) because the answer is brotli-compressed; its core matches `head`'s when the edge has the store's current copy.

The covers are deterministic: `prepare.ts`'s encoder, run on 20943's cover, gives the same bytes and therefore the same content-addressed keys as the hand publish put up.

## Decision

A cover-only path, `scripts/media/publish-covers.ts` (logic in `cover-publish.ts`), runs as a step of the News workflow after the polls and before the commit.

| Concern | Choice | Reason |
| --- | --- | --- |
| What it looks for | Comm-Links on record (latest revision, not under takedown) published in the last 14 days (`--recent-days`) that the live manifest has no cover for. When there are none, the run makes no request to RSI. The first RSI request waits the 5 s spacing too, since the polls of the same job have just asked RSI | The 22 older Comm-Links without a cover (Q&As, patch notes, the DefenseCon pages) are not on the hub and never will be; the window keeps every run from hunting for those. A new Comm-Link that is not on the hub (patch notes, as a rule) is looked for for 14 days: three hub pages a run, about 36 requests a day, within section 9's rate. A new Comm-Link that is on the hub is on its first page |
| Where from | RSI's Comm-Link hub, newest first, up to 3 pages (`--pages`), stopping once every candidate is found; then each cover once. One request every 5 s, the project User-Agent with the contact address (CLAUDE.md section 9). A first page with no transmission halts the run (section 5) | The same source and rate as `fetch-covers.ts` (ADR-029) |
| The copies | `cover-renditions.ts`, the encoder `prepare.ts` now also calls: WebP at 1920, 1280, 960, 640 and 480 px, never upscaled. Uploaded under the content-addressed keys of ADR-034 (`media/covers/<id>-<w>-<hash12>.webp`, a year's cache), skipping keys the store already holds | One encoder, so the CI path and the hand publish reach the same keys |
| The manifest | Read with the store's strong ETag (`head`) and bytes whose ETag matches it (`get`); while the edge still serves an older copy the read waits for the purge, 10 s at a time for up to two minutes, so a merge is never based on stale bytes. The new covers are added (newest id first); `generated_at` is set to the time of the write; every other field and every cover already there is carried over as read and checked to be identical (`assertOnlyCoversAdded`); the result is validated against `MediaManifest`. Written with `ifMatch` on the ETag read; on a 412 it reads again and merges again, three times at most. A 412 that answers the SDK's own repeat of a write that landed (the first answer lost) is recognized: the live covers are this run's, byte for byte, and the run carries on | Read-modify-write that never drops another entry and never overwrites a manifest another writer put up meanwhile |
| The hand publish | `publish-sync.ts` now reads the live manifest from the store before it uploads anything and refuses a manifest that lacks a cover the live one has (the checkout has not fetched the covers CI added: run `fetch-covers.ts` and `prepare.ts` first), unless `--allow-cover-drop` (a takedown). Its manifest write is conditional on the ETag it read | The other writer. Without the guard, the owner's next publish from a checkout without CI's covers would take them off the site |
| The rebuild | The step adds a row per new cover to the committed `fixtures/rsi-media/cover-sources.json`, which the workflow's commit step now stages. That commit to main redeploys the site, whose build fetches the new manifest (ADR-034). Before the step ends it reads the manifest back through the CDN until it is the new one (up to six minutes) and at least one minute has passed since the write, the purge's reach across edges | No deploy hook or second secret: the data commit the workflow already makes is the trigger, and it comes after the CDN serves the new manifest. A cover found in a run that collected no news still lands a commit |
| Credentials | The repository secret `BLOB_READ_WRITE_TOKEN`, the store's read-write token, given only to this step. Without it the step is a dry run (`--dry-run-without-token`) that reads the manifest through the CDN and writes nothing. `CDN_BASE_URL` is written into the workflow: it is the store's public address, not a secret | The owner adds the secret; nothing else changes when he does |
| Failure | `continue-on-error`: a failed cover step never holds back the news commit. The run's state is the live manifest, so a failed run is retried by the next one | GitHub runs the cron late and unevenly; nothing here depends on timing |
| Proof without writing | `--dry-run` plans, merges and checks without writing; `--rehearse <ids>` runs the whole path as if those covers were not up, whatever the Comm-Link's age, and reports whether the planned keys are the live ones. The workflow's manual run takes the ids as an input | A way to show the path works before the secret exists, and later on the runner itself |

## Alternatives considered

| Option | Why not |
| --- | --- |
| Run `prepare.ts` and `publish.ts` in CI | CI has none of the media; the manifest it built would drop every picture |
| Download every media file into CI, then prepare and publish | 1.7 GB per run, and the CIG pictures would be rebuilt from copies of themselves; the cover is the only thing that changes between hand publishes |
| A second manifest (`covers.json`) for the site to merge at build | Two mutable objects instead of one, a change to `apps/web/scripts/media-manifest.ts` and `lib/media.ts`, and the hand publish would still have to reconcile them |
| Read the manifest through the CDN and overwrite unconditionally | The edge may hold an older manifest until its purge lands; a merge on it can drop whatever was written since, and so can a concurrent writer |
| Make the store private to read past the edge | The site and browsers read the media from the public URL (ADR-034) |
| A Vercel deploy hook to rebuild the site | A second secret for the owner to add, and a rebuild that could run before the CDN serves the new manifest; the data commit is already there |
| A separate workflow on its own schedule | Twice the runner start-up minutes, and the ordering with the news commit (cover first, then the push that redeploys) would be lost |
| Look for every Comm-Link without a cover, as `fetch-covers.ts` does | Six hub pages or more every two hours for 22 Comm-Links the hub does not list |

## Consequences

- New: `scripts/media/publish-covers.ts`, `cover-publish.ts`, `cover-renditions.ts`, `blob-env.ts` (the credential loader, moved out of `publish.ts`); tests in `scripts/__tests__/media-covers-ci.test.ts`, `media-cover-renditions.test.ts` (the real encoder), `media-blob-read.test.ts` (the adapter's read, the SDK replaced) and an in-memory store with ETags and conditional writes in `scripts/__tests__/fake-media-store.ts`, which `media-publish.test.ts` now shares.
- `blob.ts`: `MediaStore.read` returns the bytes with the store's strong ETag, waiting out a stale edge copy (before, it returned the edge's bytes alone); `put` takes `ifMatch`; a lost conditional write is classified 412 and not retried blind. `publish-sync.ts` and `publish.ts` gain the cover guard, `--allow-cover-drop` and the conditional manifest write. `fetch-covers.ts` and `prepare.ts` share the record reader and the encoder.
- `.github/workflows/news.yml`: the cover step, the `rehearse_covers` input, `cover-sources.json` in the commit, and the job's timeout from 40 to 55 minutes. A run with no candidate costs one manifest read; a run that publishes adds RSI's few requests and one to six minutes of waiting on the CDN.
- `generated_at` now means the manifest's last write, by either writer, not only the last `prepare.ts`.
- A cover published by CI is in the store and the record but not in the owner's `fixtures/rsi-media/covers/`. His next hand publish refuses until `fetch-covers.ts` has copied it (the fetch already re-fetches a recorded cover whose file is missing) and `prepare.ts` has rebuilt. `docs/runbooks/media.md` says so.
- Not changed: a cover already published for a Comm-Link later put under takedown stays in the manifest until a hand publish without it (`--allow-cover-drop`). CLAUDE.md section 5's one-cycle purge for takedowns has never covered the media manifest; this ADR leaves that as it was.
- CLAUDE.md section 9: `BLOB_READ_WRITE_TOKEN` is now also the News workflow's secret, for this step alone. Section 4: `scripts/media/publish-covers.ts` runs in CI. ADR-029's "a cover appears after a local run of the fetch" and ADR-034's "never from CI" read with this record.
- The audit (a fresh session, 2026-11-11) found that the first version read the manifest through the edge while claiming not to, and that a lost answer, the first RSI request after the polls, the redeploy's timing and rehearsals of older ids needed handling; all are handled above. Not yet shown: that the runner's encoder gives the same bytes as the owner's Windows build. If it does not, the cost is extra keys, never a wrong picture; a rehearsal on the runner (`rehearse_covers`) answers it.
